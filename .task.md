# Implementation Plan: Optimize Bundle Size and Lazy-Load Heavy Components

## Task Summary

Optimize the Next.js 16 / React 19 bentosite portfolio so heavy client-only features are loaded only when needed, while preserving the existing portfolio UX:

- boot sequence into the dashboard
- Three.js / React Three Fiber model and map viewers
- chatbot behavior and chat persistence
- `/scrollable`, `/projects`, and `/playground` route behavior
- dark/light theme and CSS-variable color system

This is a planning-only document. Do not implement from this branch analysis until the plan is approved.

## Current Baseline

### Build Baseline Is Blocked

`npm run build` currently fails before route bundle stats are produced:

```text
src/app/scrollable/_components/ScrollableHero.tsx:48:13
Property 'onProjectsClick' does not exist on type 'HeaderProps'.
```

`ScrollableHero` passes `onProjectsClick={onOpenProjects}` to `Header`, but `src/components/Header.tsx` does not define that prop. This must be fixed or removed before capturing meaningful bundle output.

Also observed during build:

- Next.js selects `/Users/bentomac/conductor/repos/bentosite/package-lock.json` as workspace root because it sees multiple lockfiles.
- The warning can be silenced by setting `turbopack.root` in `next.config.ts`.
- `baseline-browser-mapping` emits a freshness warning; this is non-blocking.

### Existing Lazy-Loading Patterns

Good patterns already in place:

- `src/app/page.tsx` dynamically imports `Viewfinder`, `Chat`, and `SkillsSection`.
- `src/app/scrollable/_components/dynamic-components.tsx` dynamically imports route sections, the 3D viewer, chat, modal, and skills.
- `src/components/Viewfinder/Viewfinder.tsx` dynamically imports individual media viewers (`Model3DViewer`, `PDFViewer`, `MapViewer`, etc.).
- `src/components/MediaViewer/MediaViewer.tsx` dynamically imports media-specific modal viewers.
- `/playground/*` game pages dynamically import individual game components with `ssr: false`.
- `src/components/Playground/BentoHub/background/VoidBackground.tsx` dynamically imports the WebGL particle canvas.
- `src/components/LazyMotion.tsx` and `LazyPanelFallback` exist as reusable primitives.

### Main Bundle Risks Found

1. **Boot sequence eagerly preloads heavy dashboard modules.**
   `src/components/BentoOS/useBootSequence.ts` imports `Viewfinder`, `Chat`, and `SkillsSection` during the boot loading bar. `src/app/page.tsx` also mounts a hidden `<Viewfinder project={null} minimal />` while booting. That intentionally pulls Three.js and related viewer code before the user reaches the dashboard, which conflicts with the bundle/lazy-load task.

2. **Dashboard is statically imported by the home page.**
   `src/app/page.tsx` imports `DashboardLayout` directly. Even though `Viewfinder` and `Chatbot` are dynamic props, the dashboard shell and its Framer Motion usage are part of the home route graph.

3. **Many components import `motion` directly instead of `m`.**
   `LazyMotion` is present, but many files still import `motion` from `framer-motion`, including:
   - `src/components/BentoOS/BootScreen.tsx`
   - `src/components/Dashboard/*`
   - multiple `/playground` route pages
   - most game components
   - several `UnifiedGrid` cards/views

   Direct `motion` imports limit the benefit of `LazyMotion`. Components under an existing `LazyMotion` boundary should use `m` where they only need DOM motion primitives.

4. **Some loading fallbacks import animation libraries.**
   `src/app/playground/reaction/page.tsx`, `src/app/playground/typing/page.tsx`, and `src/app/playground/rhythm/page.tsx` import `motion` just to animate "Loading...". Loading screens should use `LazyPanelFallback` or static CSS so fallbacks do not pull Framer Motion into a route earlier than needed.

5. **Projects and Playground pages eagerly import card renderers outside the dynamic grid.**
   `src/app/projects/page.tsx` imports `ProjectCard` directly.
   `src/app/playground/page.tsx` imports `GameCard` directly.
   The pages dynamically import `UnifiedGrid`, but the card components still enter the route chunk eagerly.

6. **`@/components/Chat` has two competing entry shapes.**
   The active import path resolves to `src/components/Chat.tsx`, while a separate `src/components/Chat/` folder also contains `Chat.tsx`, hooks, storage, parts, and `index.ts`. This is not necessarily a runtime bundle issue today, but it makes the public entrypoint ambiguous and easy to regress.

7. **`src/components/Dimension/index.ts` re-exports scene internals.**
   The public barrel exports the default viewer plus scene primitives. Since `Dimension` pulls Three.js, keep the public surface narrow so non-viewer imports cannot accidentally drag scene modules into unrelated chunks.

8. **The size budget is coarse.**
   `.size-limit.json` checks all `.next/static/chunks/**/*.js` against `1.5 MB` gzip. That catches total JS growth, but it does not identify route-level first-load regressions.

## Goals

- Produce a clean production build and measurable baseline.
- Reduce initial home route JS by deferring dashboard/viewer/chat/game code until the route or UI state needs it.
- Keep WebGL/Three.js and browser-only APIs behind `ssr: false` dynamic boundaries.
- Replace animation-heavy loading fallbacks with lightweight shared fallbacks.
- Keep route-specific UX and visual output stable.
- Keep imports aligned with existing module/barrel conventions.
- Preserve current test coverage and add narrow checks only where behavior is refactored.

## Non-Goals

- Do not redesign the UI.
- Do not change project content, chat copy, or localStorage schema.
- Do not remove animations broadly; reduce where code splitting benefits, but keep intended motion semantics.
- Do not add new dependencies.
- Do not rewrite the Three.js viewer internals unless required for bundle isolation.

```text
src/app/projects/
├── page.tsx                     # thin route shell
└── _components/
    └── ProjectsGridClient.tsx   # dynamic grid + ProjectCard renderer
```

This keeps `UnifiedGrid`, card renderers, and route-specific client state in one lazy-loaded client chunk per route.

### Phase 1: Stop Boot From Pulling Heavy Chunks Early

Files:

- `src/components/BentoOS/useBootSequence.ts`
- `src/app/page.tsx`

Plan:

1. Remove heavy module preloads from `PRELOAD_MODULES`:
   - `@/components/Viewfinder`
   - `@/components/Chat`
   - `@/components/Skills/SkillsSection`

2. Preserve the boot bar timing and visual rhythm by replacing module-count progress with deterministic phase progress, or with only tiny non-heavy preloads.

3. Remove the hidden boot-time `<Viewfinder project={null} minimal />` mount from `src/app/page.tsx`.

4. If perceived dashboard readiness suffers, schedule optional warm-up after boot completion with `requestIdleCallback` or a short `setTimeout`, but do not block first paint or boot completion on Three.js.

5. Verify:
   - boot screen still reaches ready state
   - skip/click/keyboard behavior still works
   - dashboard still crossfades in correctly

Risk:

- The boot bar currently implies real module loading. If this is changed to deterministic progress, keep timings and labels stable so the user-facing boot experience does not feel broken.

### Phase 4: Convert Eligible Framer Motion Usage to `m`

Files to prioritize:

- `src/app/page.tsx`
- `src/components/BentoOS/BootScreen.tsx`
- `src/components/BentoOS/TerminalPrompt.tsx`

- `src/components/Dashboard/ViewfinderPanel.tsx`

Plan:

1. Use existing `LazyMotion` boundaries where present.

2. Convert `motion.*` to `m.*` in components that only use basic DOM animations, variants, hover/tap, and `AnimatePresence`.

3. Keep direct Framer Motion imports where hooks are required:
   - `useMotionValue`
   - `useSpring`
   - `useTransform`
   - `useAnimationFrame`

4. If a converted component can render outside a `LazyMotion` provider, wrap the owning route/shell with `LazyMotion` or `MotionProvider`.

5. Verify animations:
   - boot enter/exit
   - dashboard stagger
   - mobile tab transitions
   - chat panel transitions

Risk:

- `m` components require a `LazyMotion` ancestor. Do not convert isolated components unless their render tree is covered.

## Acceptance Criteria

- Production build succeeds.
- Existing lint, type-check, unit tests, and size check pass.
- Home route no longer boot-preloads `Viewfinder`, `Chat`, and `SkillsSection`.
- Hidden boot-time 3D viewer preload is removed or deferred until idle after dashboard readiness.
- Dashboard shell is not statically bundled into the initial boot route when it can be lazy-loaded.
- Game route loading screens use shared lightweight fallbacks.
- `/projects` and `/playground` no longer eagerly import card renderers outside their lazy route clients.
- Public heavy-feature barrels are narrower and do not expose internals by default.
- User-visible behavior remains unchanged except for faster/lighter loading.
